# ロードマップ

Tascal の段階的な構築計画。各マイルストーンに**目標 / 含む作業（チェックボックス） / 完了条件**を持たせ、
進捗を追跡できるようにする。チェックボックスは作業の進行に合わせて更新する。

> 多くのマイルストーンは `open-questions.md` の決定に依存する（🔴）。決定前は「設計のみ」までしか進めない。

## 決定の反映（2026-06-18）
- **段階拡張**で進める（Q-STRAT-1）。**M0 が出発点**。
- デスクトップ = **Electron**（Q-ARCH-1）。モバイルは将来 Swift / React+Capacitor で別系統。
- **当面ローカル継続**（Q-ARCH-2）。→ **マルチユーザー（M2）とホスト型 AI は「Web サービス展開」段階まで後ろ倒し**。
- **AI は当面保留**（Q-AI-1）。着手時は提案のみ最小から。長期の北極星は「AI 社員のマネジメント」。

そのため当面の主戦場は **M1（Electron 化・コード基盤）→ M4（コミットメント可視化、ローカルで実装可）**。
M2 / M3 は Web サービス展開の判断後に本格化する。

## M0 — プロトタイプ ✅ 完了

**目標**：Tascal の世界観と基本タスク体験を、触れる形で確立する。

- [x] タスク / プロジェクト / タグ / 優先度 / 締切 / サブタスク
- [x] 今日・今後・すべて・プロジェクト別・タグ別・カレンダー の各ビュー
- [x] 詳細ドロワー、達成リング、ダーク/ライトテーマ、完了アニメーション
- [x] `localStorage` 永続化、デザインシステム（DESIGN.md）
- [x] pnpm / Node LTS / CI（型チェック + ビルド）

**完了条件**：上記が動作し、ビルドが通る → 達成済み。

## M1 — 基盤整備（Electron 化含む）⬜ ← 次の主戦場

**目標**：「Web + デスクトップ（Electron）」を出せる土台と、拡張に耐えるコード構成を確立する。

- [ ] **Electron シェルの最小構成**（メイン/レンダラ分離、現プロトタイプをレンダラに載せる）
- [ ] レンダラ（Web）とメインプロセス（Node）の責務境界・IPC 方針を定義
- [ ] モノレポ化の要否・タイミングを決定（Q-ARCH-5）、必要なら `packages/` へ再編
- [ ] 共有コア（`core`/`ui`）の切り出し方針を確定（Q-ARCH-4）
- [ ] テスト基盤（Vitest / Playwright）の導入
- [ ] デスクトップの最小ビルドが生成できる（署名・自動更新は M5 以降 / Q-ARCH-6）

**完了条件**：同一コードから Web とデスクトップ（Electron）が起動・ビルドできる。

**着手条件**：Q-ARCH-2（データ基盤）を確定すること。

- [ ] データ基盤を決定（Q-ARCH-2）＋オフライン要件の確定（Q-ARCH-3）
- [ ] 認証 / サインイン
- [ ] Workspace / Membership、共有プロジェクト
- [ ] タスクの担当者割り当て、「自分の約束」ビュー
- [ ] `localStorage` データの移行インポート
- [ ] 変更履歴（ActivityLog）と基本通知

**完了条件**：2 アカウントでプロジェクトを共有し、担当者割り当てと同期ができる。

## M3 — AI 協働 基盤 ⏸ 保留

**目標**：エージェント提案の最小形（Triager + Planner / `suggest` ティア）を動かす。
**メモ**：当面保留（Q-AI-1）。デスクトップなら Electron メインプロセス＋OS セキュアストレージで
ローカル実行も可能（ホスト型バックエンド不要）。Web 展開時はサーバープロキシへ移行。

- [ ] AI 実行をサーバープロキシで確立（Q-AI-3、キーは非クライアント）
- [ ] プロバイダ/モデル方針の確定（Q-AI-4）、抽象化レイヤ
- [ ] 内部 API をツールとして公開（read/create/update、破壊的操作は承認必須）
- [ ] エージェント・インボックス UI（提案の承認/却下/編集）
- [ ] 権限ティアの実装（Q-AI-2、既定 `suggest`）
- [ ] Triager（振り分け提案）、Planner（サブタスク案）
- [ ] コンテキスト範囲・プライバシー方針の明文化（Q-AI-5）、コスト上限（Q-AI-6）

**完了条件**：新規タスクに AI が振り分け案を出し、人が承認すると反映される。

## M4 — コミットメント可視化 ⬜

**目標**：「約束」とそのリスクを中心に据えた体験を完成させる。

- [ ] コミットメントのモデル確定（Q-PROD-2）：状態 / 相手 / 努力目標 等
- [ ] 遅延リスク算出（Q-PROD-3：ルール and/or AI）と表示
- [ ] ダッシュボード / レビュービュー（週次・期限遵守率・遅延集約）
- [ ] Watcher（リスク監視）と Briefer（日次ブリーフィング）
- [ ] North Star 指標の計測（Q-PROD-1）

**完了条件**：「危ない約束」が一目で分かり、AI が能動的に警告・ブリーフィングする。

**目標**：外部ツールと繋ぎ、取りこぼしをさらに減らす。速度 UX を磨く。

- [ ] 優先連携の決定（Q-PROD-5）と実装（カレンダー / Slack / GitHub / メール 等）
- [ ] Scribe（チャット/議事録/メールからのタスク抽出）
- [ ] 通知（デスクトップ通知 / リマインダー）、繰り返しタスク
- [ ] 検索 / コマンドパレット / キーボードショートカット
- [ ] デスクトップ署名・自動更新・対象 OS 確定（Q-ARCH-6）

**完了条件**：少なくとも 1 つの外部連携が機能し、通知で締切を逃さない。

## M7 — AI 社員のマネジメント 💤 北極星（長期）

**目標**：AI 社員にミッションを与えて自律実行させ、必要時にユーザーへエスカレーション（Post）する。

- [ ] 実行基盤の確立（常駐 / ジョブ、Q-AI-7）— Web/バックエンド方針に依存
- [ ] ミッション・権限・責務モデル（Q-AI-9）。AI 社員をコミットメント可視化の対象に

**完了条件**：与えたミッションを AI が進め、判断が要る時だけユーザーに上げてくる体験が成立する。

## 運用メモ
- マイルストーンは厳密な順序ではなく、決定が済んだ領域から並行して進めてよい。
- 各タスクの細目・受け入れ基準は、着手時に Issue / タスクとして具体化する。
- 大きな進捗があったらこの表とチェックボックスを更新する。
