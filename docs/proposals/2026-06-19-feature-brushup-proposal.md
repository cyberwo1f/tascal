## ⚠️ 追補（2026-06-19・ユーザー決定で更新）

本レポート §4.1 はコミットメント表現を「**ハイブリッド案（属性拡張＋softDue/stakeholderは後ろ倒し）**」と推奨していたが、
ユーザーとの議論を経て**以下に更新（[ADR-0001](../adr/0001-commitment-model.md) として確定）**：

- **Q-PROD-2 → 第一級エンティティ化**：Commitment が複数 Task を束ねる構造を採用。コンセプト「一人ではやり切れない規模＝1約束が複数作業に枝分かれ」を直接体現する。§4.1 の「案A 寄り・最小核に絞る」推奨は、**現状行動への最適化＝プロダクトが超えようとする規模の自己否定**という指摘を受けて撤回。
- **柱①との両立 → 段階開示・原則任意**：リッチな項目はスキーマに持つが UI は段階開示。単独ユーザーは今と同じ軽さ。検証はデータモデル＋ダッシュボードで行い入力を強制しない。
- **シーケンス → M4 と AI 最小形（M3）は分離維持**：AI 実装**前**に人手で構造を検証（de-risk）。最終形（落としどころ）は「リッチモデル＋**AI による構造の充填**＋段階開示」。
- **ミッション追加**：「**AI 格差をなくし、AI をより身近にする**」を vision.md に反映。

§6 の「softDue/stakeholder/ownerType を後ろ倒し」は**任意・段階開示として残す**形で維持（=スキーマには持つが入力強制しない）。
North Star（§3/§8 の Q-PROD-1）と遅延リスク（Q-PROD-3）は**未確定の提案のまま**。

## 0. このレポートの読み方

各提案には次のメタを付けている：**柱**（①一人特化 ②マルチタスク ③コミット可視化 ④AI協働）／**Q-ID**（関連未決事項）／**MS**（想定マイルストーン M1〜M7）／**優先度**（高/中/低）。
依頼の4点を全カバーしている：(a)現状ブラッシュアップ=§2 / (b)追加機能=§3 / (c)衝突・不整合=§5 / (d)効果薄→代替案=§6。

**最重要の構図（チーム合意）**：Tascal の差別化の核（柱③コミットメント・柱④AI）は**まだ未実装**で、データモデルに `status/owner/stakeholder/risk` が無い。一方ビジョンは強固。よって本提案の主眼は「**足回りの速さ（柱①②）を M1 で固めつつ、柱③の最小核を M4 で正しく入れる。ただし"全部入り"は柱①(設定最小)を壊すので段階繰り延べする**」こと。

### 1.3 「やめる/簡素化/後ろ倒し」の主要判断（§6で詳述）

- **softDue（二重締切）/ stakeholder / ownerType を M4 で一括導入しない** → 柱①(設定最小)に最も反する。**status＋単一due＋派生リスクの最小核に絞り、共有(M2)・AI着手フェーズへ段階繰り延べ**。
- **「AI社員」は社内の長期北極星に留め、対外コピーは「アシスタント/秘書」** → agentwashing による期待過剰→失望→解約リスクの回避。機能が約束に追いついてから名乗る。
- **請求・入金フォローAI は旗艦から外す** → 非目標(工数会計/請求書発行)と衝突＋飽和市場。やるなら「入金待ちコミットメントの遅延可視化」に純化。
- **T1の追加機能11個を5本に圧縮**（⌘Kに検索/ショートカットを内包、startDate・密度切替・繰り返し2モードは後ろ倒し/簡素化）。
- **週次レビューは"儀式"でなく5分の軽量版**（やらなくても日常UXが成立する設計）。

## 2. 現状機能のブラッシュアップ提案（柱①②中心）

現状: `Task{id,project,title,done:boolean,priority,due:'YYYY-MM-DD'|null,tags[],subs[],notes?}`、ソートは `優先度→締切` 固定（`src/selectors.ts`）、永続化は `localStorage` の `tascal.v1` 単一キー。

| 項目 | 柱 | 現状の課題 | 改善案 | 価値仮説 | 優先度 | MS |
|---|---|---|---|---|---|---|
| **締切の自然言語入力**（P1） | ① | 追加バーはtitleのみ。締切は詳細ドロワーを開く2手間。today/upcoming以外で追加すると`due=null` | 入力中に「明日17時」「来週月曜」を解釈し締切を自動セット。**パース箇所をハイライト**して誤認識を即確認 | 1行で放り込む体験＝導入即日と速さの核 | 高 | M1 |
| **追加バーからの即メタ指定**（P1） | ①② | 優先度は循環ボタンのみ、project/tagは追加バーから不可 | `#tag` `/project` `!1/!2/!3` をトークン解釈しチップ化（※`@`は将来のowner用に温存＝N-3対策） | 文脈切替なしで1タスク完成。「後で整理」を消す | 高 | M1 |
| **ソートの柔軟化（固定→選択可）** | ② | `優先度→締切` 完全固定 | ビューごとに 優先度/締切/手動/プロジェクト から選択。**手動順を選んだ時だけD&D有効化**し自動ソートと排他（Todoist方式） | 「次に何をやるか」の判断軸をユーザーが選べる | 中 | M4 |
| **横断グループビュー**（P7） | ② | 「すべて」はフラット。プロジェクト跨ぎで"今やれる"を一望できない | 今日/今後をプロジェクト見出しでグループ表示（折りたたみ可）。`projectCount`の拡張で済む。※横断では手動順は無効=自動ソートのみ（N-1対策） | 複数案件同時進行＝柱②の直球 | 中 | M4 |
| **期限超過の扱い** | ②③ | 「今日」= `due===today`のみ。期限超過が「すべて」に埋もれる | 期限超過を「今日」先頭に常時集約 | 「漏れない」感覚 | 中 | M4 |
| **完了済みの軽量化** | ① | `showDone`が全ビュー共通の単一トグル、完了が常駐 | 既定で畳む＋「今日完了分のみ」など軽い粒度。古い完了は視界外へ | 達成感は残しつつノイズ減（静か） | 低 | M4 |
| **キーボード到達性** | ① | フォーカスリング/aria-labelは整備済だがマウス前提操作が中心 | §3のショートカットと一体で 行選択→Space完了/E編集 等の経路 | キーボードのみで完結＝速さの土台 | 中 | M1 |

> **後ろ倒し（§6参照）**: 「今日」の意味を `startDate`(着手予定)で再定義する案は、概念追加を1フェーズ1つに絞るため M1 から外し M4 のコミットメント整備と同時に1度だけ行う。

## 4. コミットメント＆AI協働の深掘り（柱③④）

### 4.1 コミットメント・データモデル（Q-PROD-2）

**推奨: ハイブリッド案** — 実装は Task 属性拡張（軽い）、将来「約束の集約」が要れば別エンティティへ切り出せる名前付け/分離を最初から意識。理由: 一人運営の実態は「1タスク=1約束」が支配的で、Linear の Cycle/Issue 分離は複数人前提＝初期は過剰。

**M4で入れる最小核（R2の段階繰り延べを反映）**:
```ts
type CommitmentStatus = 'todo' | 'doing' | 'done' | 'blocked';
// late（遅延）は status に入れない → due超過かつ未完を派生算出（当日依存のため保存しない）

interface Task {
  /* 既存: id, projectId, title, priority, tags, subs, notes? */
  status: CommitmentStatus;   // done:boolean からの互換移行（tascal.v1→v2）
  due: string | null;         // 「対外的な約束の期日」。当面これ1本（softDueは入れない）
  ownerId?: string | null;    // 任意。単独利用は省略（=自分）。共有(M2)で顕在化
  createdAt; updatedAt; source?: 'manual'|'ai'|'integration:<name>';
}
```

**段階繰り延べ（§6・R2）**: `softDue`（二重締切）・`stakeholder`・`ownerType:'human'|'ai'` は **M4で入れない**。
- `softDue`→ 当面はメモ/タグで代替。複数人で締切認識がズレる共有フェーズで再検討。
- `stakeholder`→ 自由記述メモ/タグ（`@顧客名`）で十分。構造化はM2(共有)と同時。
- `ownerType`→ owner=ai のタスクは Q-AI-7 保留中は存在しない。AI着手フェーズで後方互換に追加（YAGNI／agentwashing回避）。

→ **ADR 化を推奨**（なぜ最小核に絞ったか・将来の拡張ポイントを保全）。

### 4.2 遅延リスクの可視化（Q-PROD-3）

- **保存 vs 派生 → 派生（毎回算出）**。残猶予は当日依存で、保存すると陳腐化（CLAUDE.md原則）。`selectors.ts` の責務。
- **初期は2要素ルール**（R2の簡素化を採用、T2の3変数式は係数が当てずっぽうになり誤判定で信頼を損なうため後回し）:

  | 判定 | 条件（例・要チューニング） | 色 |
  |---|---|---|
  | 🔴 危険 | 未完了かつ `due`超過 / `残猶予≤1日 かつ サブ進捗<80%` | 赤 |
  | 🟡 注意 | `残猶予≤3日 かつ サブ進捗<50%` | 黄 |
  | ⚪ 安全 | 上記以外 / done | 無彩色 |

- `statusPenalty`（blocked加点）と **AI補強**（notes/サブ文面から「外部依存待ち」等を推定し格上げ提案）は**実データで誤判定を見てから**追加。AIスコアは `source:'ai'` の派生キャッシュとして持ち、ルールスコアと両方表示（透明性）。
- **しきい値は推測**（Tascal固有データが無いため。計測導入後にチューニング前提）。
- UI: カードの締切バッジ横に小さなリスクドット（安全時は無表示＝静か）。ホバーで「なぜ赤か」を一行（透明性）。

### 4.3 ダッシュボード／レビュービュー

既存「今日の達成リング」を約束視点へ拡張（すべて `selectors.ts` の派生でローカル完結）:
1. **危ない約束（最上段に集約）**: 🔴🟡 を件数バッジ付きで上位に（Asana の on track/at risk/off track の3段に対応）。
2. **今週のコミットメント**: `due`が今週内のTaskを 危険→注意→安全 順（Linear のサイクル=週の約束の器、を一人運営向けに週へ縮約）。
3. **期限遵守率**: 直近N週で「期日までに done / 期日が来た約束」。※社内メトリクス用途中心、ユーザー面は「安心系」の見せ方（§4.4・§6）。
4. **達成リング拡張**: 今日→週/プロジェクト/担当者の軸切替。担当者軸は将来 human+ai が並ぶ（柱④の伏線）。
5. **週次レビュー（軽量版）**: 「儀式」でなく**5分で終わる振り返り**（やり残し＋繰り越しワンタップ）。やらなくても日常UXが成立する設計（§6・GTD週次レビューの離脱主因対策）。

### 4.4 AI協働 段階ロードマップ（Q-AI-1/7）

| 段階 | 役割・自律度 | ティア | ローカル(Electron)成立 |
|---|---|---|---|
| **D0**（M3着手時） | Triager(振り分け案)＋Planner(サブタスク案) | suggest | ◎（鍵はElectronメイン＋OSセキュアストレージ。ホスト型不要） |
| **D1** | Watcher(遅延警告)＋Briefer(朝のブリーフィング) | suggest/一部 act_with_approval | ◎ ほぼ（常駐=アプリ起動中。完全常駐は△） |
| **D2** | 低リスク操作（タグ付け等）を承認付き実行 | act_with_approval | ○（破壊操作は除外・ActivityLog＋取消） |
| **D3** | 無害カテゴリのみ自動 | auto（カテゴリ単位） | ○（起動中に限る） |
| **D4 = AI社員（北極星/M7）** | ミッション付与→自律実行→例外時Post | カテゴリ別＋ミッション単位 | △ **不十分**。"閉じていても動く"には**バックエンド常駐**が必須 |

- **決定的ライン**: D0〜D3 はローカル Electron で前進可。**D4（AI社員）で初めてバックエンド常駐が必須**になり、Web展開判断（Q-ARCH-2）と直結。
- **対外フレーミング（R2）**: 当面の機能は suggest 中心。「AI社員」は**社内の長期北極星に保持**し、対外コピーは**「アシスタント/秘書」**（"危ない約束を見張り、危ない時だけそっと教える"）。end-to-endで仕事を完遂できてから「社員」を名乗る（agentwashing による期待過剰→失望→解約の回避）。
- **割り込まない原則の徹底（N-4）**: AIの出力は原則エージェント・インボックスにバッジで溜める。OSポップアップは「時間依存の確定警告」に限定。ブリーフィングはpull型（開いたら見える）を既定に。

### 4.5 AI社員シナリオ（Q-AI-7〜9）— 優先度を再整理

人間とAIを**同じコミットメント軸**で見せる（AI社員も owner=ai として Task を持ち、担当者別リングに人間と並ぶ）。Postは3型: **エスカレーション（判断）/ 確認（承認）/ 回答要求（情報不足）**。

| 優先 | シナリオ | 内容 | 判定（R2） |
|---|---|---|---|
| **1（旗艦）** | **案件トリアージ＆遅延見張りAI** | 受信依頼を約束として整え、遅れそうな自分の約束を前日までに通知。Triager＋Watcher | ◎ 非目標と衝突せず・Tascalデータで完結・suggestで価値。北極星への最短経路 |
| 2 | 定例業務委任AI（週報・状況確認） | 週次で先週クローズ分から週報ドラフト、未更新の約束の担当者へ確認を促す | ○ M2(共有)以降・外部連携前提 |
| 3（非旗艦化） | 請求・入金フォローAI | （元案）請求書ドラフト＋入金督促 | ✖→純化: 非目標(工数会計/請求)衝突＋飽和市場。**「入金待ちコミットメントの遅延可視化」に限定**し発行/会計は外部連携 |

## 6. 効果が薄い／リスクのある項目と代替案（R2）

| 項目 | 判定 | 理由 | 代替案 |
|---|---|---|---|
| `softDue`＋`due` 二重締切を M4 で導入 | **簡素化**（当面 単一due） | 「どっちに入れる？」の判断コストが毎回。柱①に最も反する。単独利用で便益が出る場面が少ない | M4は`due`単一。努力目標はメモ/タグ。二重化は共有フェーズで限定再検討 |
| `stakeholder` を M4 でフィールド化 | **後ろ倒し** | 単独では頭の中にあり構造化価値が薄い（I-5/I-8） | 自由記述/タグ(`@顧客名`)。構造化は M2(共有)と同時 |
| `ownerType:'human'｜'ai'` を M4 に入れる | **後ろ倒し** | owner=ai のタスクは Q-AI-7 保留中は不在。使わない列＝設定最小に反し意味変更リスク（YAGNI/agentwashing） | human前提で `ownerId?` 任意のみ。ownerType は AI 着手時に後方互換で追加 |
| 週次レビュー儀式を機能の柱に | **簡素化** | 一人運営で定着率が構造的に低い（GTDで離脱主因） | 5分の軽量版＋やらなくても成立する設計。専用モードの作り込みは後回し |
| 請求・入金フォローAI を旗艦に | **やめる/非旗艦化** | 非目標(工数会計/請求書)と衝突＋飽和市場 | 「入金待ちコミットメントの遅延可視化」に純化、発行/会計は外部連携。旗艦は②遅延見張りに |
| startDate＋「今日」再定義を M1 で | **後ろ倒し** | M1の主目的はシェル移行。概念追加は混乱要因。1フェーズ1概念 | M4のコミット整備と同時に1度だけ。当面「今日」は締切今日/超過のまま実害小 |
| 繰り返し 完了基準/固定基準の2モード | **簡素化** | 初手から両モードは設定過剰 | M1は固定基準1モードのみ。完了基準は要望後 |
| 密度切替UI を M1 で | **後ろ倒し** | 「設定を増やす」典型。優先度低 | まず良いデフォルト密度を1つ。切替は後 |
| 遅延リスク 3変数式 | **簡素化**（初期） | 初期はデータ無く係数が当てずっぽう→誤判定で信頼喪失（オオカミ少年化） | 初期は2要素ルール。statusPenalty/AI補強は誤判定を見てから |

## 7. 優先度付きロードマップ提案

既存 M1〜M7 に対応づけた実行順（local/Electronで完結する範囲を優先、マルチユーザー/ホスト型AIは後ろ）。

### M1（Electron化・基盤）— "速さ"を完成させる
- 高: **P1 高速キャプチャ**（NLP＋トークン、N-3名前空間） / **P2 ⌘K統合**（検索・ショートカット内包） / **P3 バックアップJSON**
- 中: ローカル通知（確定警告限定・N-4） / クイック入力小窓 / キーボード到達性
- ※ startDate・密度切替・繰り返し2モードは持ち込まない（§6）

### M4（コミットメント可視化）— モデル確定後に着手
- **前提**: Q-PROD-2/3 を確定（§8）してから実装開始
- 高: **P4 status化＋遅延の派生算出** / **P5 2要素リスク＋危ない約束ダッシュボード** / **P7 横断グループビュー＋期限超過集約**
- 中: ソート柔軟化＋排他D&D（N-1） / 繰り返し（固定基準） / 達成リング拡張 / 軽量週次レビュー
- ※ owner/stakeholder/softDue/ownerType は入れない（共有・AIフェーズへ）

### M3（AI協働 最小形）— ローカルElectronで成立
- **P6 トリアージ＆遅延見張りAI（D0 suggest）→ D1 Watcher/Briefer**。出力はインボックス（割り込まない）。対外は「アシスタント」フレーミング。

### M5 / M2 / M7（後続）
- M5: 連携（カレンダー/Slack/メール）・通知UX強化（Q-PROD-5 優先付け要）
- M2: マルチユーザー＝この時に stakeholder/owner を構造化（Q-PROD-4 権限モデル）。Web展開判断とセット
- M7: AI社員（D4）。バックエンド常駐が必須＝Q-ARCH-2/Q-AI-7 と直結

### 「次の3テーマ」（CLAUDE.md再開ポイント）への対応
1. 機能洗い出し → 本レポート §2/§3 で4本柱に紐づけ済み
2. コミットメントモデル確定 → §4.1（ハイブリッド＋最小核）＋ADR推奨。**Q-PROD-2/3を最優先で決める**
3. AI社員像の具体化 → §4.5 シナリオ3本（旗艦=遅延見張り）＋§4.4 フレーミング指針
