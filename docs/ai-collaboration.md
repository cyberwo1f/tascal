# AI エージェント協働の設計

Tascal の中核差別化。AI を「受け身のアシスタント」ではなく **「能動的なチームメイト」** にする。
ただし**主導権は常に人間**にあり、エージェントの行動は権限と承認で制御する。

すべて **🟡 提案 / 🔴 未決** 段階。重要論点は末尾と `open-questions.md` に集約。

> **現フェーズの方針（2026-06-18 決定）**：AI は**当面保留**（まず M0→基盤を固める）。
> 着手するときは「提案のみ最小（Triager+Planner / `suggest`）」から。**長期の北極星は「AI 社員のマネジメント」**（§7）。

---

## 1. 設計思想

| 原則 | 内容 |
| --- | --- |
| **能動性（Proactivity）** | 聞かれる前に整える・気づく・提案する。ただし“割り込まない”。提案は専用面にそっと溜める。 |
| **人間が主導（Human-in-control）** | 既定は「提案 → 人が承認 → 実行」。自動実行は明示的に許可した範囲のみ。 |
| **透明性** | 何を根拠に・何をしたかを必ず記録（ActivityLog）。取り消し可能に。 |
| **最小権限** | エージェントはカテゴリ単位の権限しか持たない。既定は読み取り＋提案のみ。 |
| **安全第一** | 破壊的操作（一括削除等）は自動化しない。API キーはクライアントに出さない（→ architecture）。 |

---

## 2. エージェントの役割（候補）

MVP で全部はやらない。優先順位は要決定（Q-AI-1）。

| 役割 | 何をするか | 起動契機 |
| --- | --- | --- |
| **Triager（振り分け）** | 新規/受信タスクにプロジェクト・優先度・締切・タグを提案 | タスク作成時（イベント） |
| **Planner（計画）** | タスクをサブタスクに分解する案を生成 | ユーザー要求 / 大きめタスク検知 |
| **Watcher（リスク監視）** | 遅延しそうな約束を検知し警告。再計画を提案 | 定期実行（日次など） |
| **Briefer（ブリーフィング）** | 「今日の約束・リスク・着手順」を朝にまとめる | スケジュール |
| **Scribe（抽出）** | チャット/議事録/メールからタスクを抽出 💤 | 連携イベント（将来） |

## 3. インタラクションモデル

```
[トリガー] → エージェント実行 → 提案を生成 → エージェント・インボックスへ
                                                  ↓
                                  人が確認 → 承認 / 編集して承認 / 却下
                                                  ↓
                                       承認時のみタスクへ反映（記録 & 取消可）
```

- **エージェント・インボックス**：提案が UI 上にそっと積まれる場所。バッジ通知。承認/却下が 1 アクション。
- **権限ティア（提案）**：
  1. `observe`：読み取りのみ（提案も出さない）
  2. `suggest`：提案を出す（既定）
  3. `act_with_approval`：操作を準備し、人の承認で実行
  4. `auto`：指定カテゴリのみ自動実行（例：タグ付けだけ自動、削除は不可）
- ティアは**エージェント × カテゴリ**で設定（Q-AI-2）。

## 4. 技術設計（提案）

### 4.1 実行場所とキー管理 🔴 重要（Q-AI-3 / Q-ARCH-2）
- 原則：**AI API キーをレンダラ（Web フロント）に置かない**。
- **デスクトップ（Electron）**：**メインプロセス（Node）＋ OS セキュアストレージ**（`safeStorage` 等）を
  “ローカルの実行層”として使い、ここから AI を呼ぶ。**ホスト型バックエンドが無くても**動かせる
  （＝当面ローカル継続の方針 Q-ARCH-2 と両立）。レンダラは「実行を依頼」し結果を受け取るだけ。
- **同期/Web フェーズ**：単独ユーザーの端末間同期やホスト型実行が絡むため、**サーバー側プロキシ**へ移行する（他者共有は非目標）。
- どちらでもクライアント（ブラウザ DOM）側にキーを露出させない点は不変。

### 4.2 モデル / プロバイダ 🟡 提案（Q-AI-4）
- 既定は **Anthropic Claude**（本リポジトリの開発文脈・ツール利用との親和性）。
  - 重い推論：上位モデル / 軽量処理：小型モデル、と用途で使い分け。
- 抽象化レイヤを設け、将来プロバイダ差し替え可能に。
- 具体的なモデル ID・コスト方針は実装フェーズで確定（最新の正確な情報は要確認）。

### 4.3 ツール利用（Tool Use / Function Calling）
- エージェントには Tascal の**内部 API をツールとして公開**する：
  `list_tasks`, `create_task`, `update_task`, `suggest_subtasks`, `flag_risk` など。
- 破壊的ツール（削除・一括更新）は**自動実行から除外**、承認必須にする。
- 将来：外部連携を **MCP** 経由のツールとして追加（カレンダー・Slack 等）。

### 4.4 能動性の実装
- **イベント駆動**：タスク作成 → Triager、締切接近 → Watcher。
- **スケジュール駆動**：日次ブリーフィング、リスク全体スキャン。
- 実行はサーバーのジョブ / スケジューラで。クライアントは結果を購読。

### 4.5 コンテキストとプライバシー 🔴（Q-AI-5）
- エージェントに渡すデータ範囲（どのタスク・どの履歴まで）を定義。
- 個人情報・顧客情報の取り扱い（マスキング / 学習に使わない等）を方針化。
- 組織ポリシー（機密・個人情報をログに出さない 等）を遵守 → `CLAUDE.md` 参照。

## 5. MVP での最小形（提案）

🟡 提案（Q-AI-1 で確定）：まずは **Triager + Planner を `suggest` ティア**で。
- 価値が分かりやすく、破壊リスクが低く、サーバー実装も比較的軽い。
- Watcher / Briefer はリスク算出ロジックとスケジューラが要るので次段階。

## 7. 北極星：AI 社員のマネジメント（長期 / 💤）

ユーザーが目指す将来像。協働（§2〜5）の延長線上にある“到達点”として記録する。

> ユーザーが **AI 社員にタスク / ミッションを与える**と、AI が**自律的に行動**し、
> **エスカレーション・確認・回答が必要なときだけユーザーへ Post** する。
> 一人経営者が“AI を雇って”AI チームを組む感覚（人間メンバーは増やさない／マルチユーザーは非目標、[ADR-0003](./adr/0003-single-person-focus.md)）。

- **AI 社員 = チームメンバー**：ユーザー本人と同様に、AI 社員も**コミットメント可視化の対象**（柱③）。
  「誰（自分／AI）が・何を・いつまでに引き受け、今どうなっているか」を一元的に見る。
  ＝**owner に AI を割り当てる委任**（owner=AI）。人間同士の割り当ては行わないが、この AI 委任は核に資するため保持する。
- **ミッション付与 → 自律実行 → 必要時に Post**：常時の監視ではなく、**例外時だけ人へ上げる**モデル。
  - エスカレーション（判断を仰ぐ）/ 確認（承認を求める）/ 回答要求（情報が足りない）を
    エージェント・インボックス（§3）の発展形として受け取り、ユーザーが返答する往復をつくる。
- **必要になる基盤**（要決定）：
  - 実行基盤：ローカル常駐か、バックエンドのジョブ/スケジューラか（**Q-AI-7**、Q-ARCH-2 に依存）。
  - エスカレーション UX：通知・承認・回答の往復設計（**Q-AI-8**）。
  - AI 社員のミッション/権限/責務モデルとデータ表現（**Q-AI-9**、data-model 拡張）。
- 段階：**まず §5 の協働（提案のみ）で「AI が役に立つ」体験を作り、自律度と常駐性を少しずつ上げる**。
  いきなり完全自律にはしない（安全・透明性・人間主導の原則を保つ）。
