# 技術アーキテクチャ

要件：**今は Web とデスクトップアプリの両方でリリースできる構成**を目標、**将来モバイル展開の可能性**。
ここでは推奨案（🟡 提案）と代替案・トレードオフを示す。確定は `open-questions.md` の決定後。

確定済みの技術土台は [`../CLAUDE.md`](../CLAUDE.md)：pnpm / Node LTS / Vite + React + TypeScript。

---

## 1. 全体像（提案）

```
                ┌─────────────────────────────────────────────┐
                │                共有コア (TypeScript)          │
                │  ドメイン型 / 状態管理 / セレクタ / API クライアント │
                │            （プラットフォーム非依存）            │
                └───────▲───────────────▲───────────────▲───────┘
                        │               │               │
              ┌─────────┴───┐  ┌────────┴────────┐  ┌───┴──────────┐
              │  Web (Vite) │  │ Desktop (Tauri) │  │ Mobile 💤     │
              │  ブラウザ     │  │ mac/win/linux   │  │ (Tauri 2 等)  │
              └─────────────┘  └─────────────────┘  └──────────────┘
                        │               │
                        └──────┬────────┘
                               ▼
                  ┌─────────────────────────────┐
                  │      バックエンド / 同期 🔴      │
                  │  認証 / データ同期 / AIプロキシ  │
                  └─────────────────────────────┘
```

中心は **UI とドメインロジックを共有コアに集約**し、各プラットフォームは“薄いシェル”にすること。
これが「Web/デスクトップ/モバイルを 1 つのコードベースで」を可能にする鍵。

---

## 2. デスクトップ + Web のシェル戦略 ✅ 決定（Q-ARCH-1）

**決定：デスクトップは Electron。Web は同じ React 資産。モバイルは将来、別系統で。**

| 方式 | 採否 | 理由 |
| --- | --- | --- |
| **Electron** | ✅ デスクトップに採用 | 実績豊富・Node エコシステムそのまま・情報量多い。**Node のメインプロセスを“ローカルの安全な実行層”**として使え、後述の AI キー局所管理にも好都合 |
| **Tauri 2.x** | ❌ 不採用 | モバイル対応が未成熟との経験的判断。モバイルまで一本化する利点を取りに行かない |
| **PWA ファースト** | 併用候補 | Web 配信自体は PWA 化して可。ただし「デスクトップアプリ」は Electron が担う |

**モバイル（将来 / 💤）**：デスクトップとは**切り離して**判断する。
- 第一候補：**Swift（ネイティブ）**、または **React + Capacitor（WebView ラップ）**。
- 背景：モバイルのクロスプラットフォームは OS 互換性・癖が大きく、ネイティブか WebView ラップが堅実という判断。
- 含意：「1 つのシェルで全 OS」は狙わない。**Web フロント（React）を Web / Electron / （必要なら Capacitor）で再利用**しつつ、
  モバイルはネイティブも選べる柔軟な構えにする。

→ 既存プロトタイプ（Vite + React）はそのまま Electron のレンダラに載せられる。レンダラ（Web）とメインプロセス（Node）の責務分離を意識して構成する。

## 3. データ基盤 / 同期 / 認証 🟡 現フェーズ決定（Q-ARCH-2）

**決定（現フェーズ）：当面はローカル継続**（`localStorage` / 将来ローカル DB）。
BaaS か自前 API+DB かは、**Web サービス展開を検討する段階**で判断する。

含意：
- **マルチユーザー共有・ホスト型 AI 実行はその段階まで保留**（柱③④の協働部分は段階的に）。
- 当面は**オフライン前提**で問題ない（Q-ARCH-3）。
- ただしデスクトップ（Electron）なら、**メインプロセス（Node）＋ OS セキュアストレージ**を
  “ローカルの実行層”として使えるため、**ホスト型バックエンドが無くても限定的に AI を動かせる**
  （キーをレンダラに出さない。詳細は [`ai-collaboration.md`](./ai-collaboration.md) §4.1、Q-AI-3）。

以下は **Web サービス展開時に再評価する選択肢**（今は決めない）：

| 方式 | 概要 | 長所 | 短所 |
| --- | --- | --- | --- |
| **BaaS（Supabase 等）** 🟡候補 | Postgres + 認証 + リアルタイムを既製で | 立ち上げ速い、認証/同期/RLS が揃う | ベンダー依存、込み入った要件で窮屈 |
| **自前 API + DB** | 例：Node/Bun + Postgres、独自認証 | 自由度高い、AI プロキシも同居 | 作る量が多い、運用負荷 |
| **ローカルファースト + 同期** | 端末にローカル DB、CRDT 等で同期（例：electric-sql / yjs / 自前） | オフライン強い、体感速い、UX が良い | 実装難度が高い、競合解決・履歴が複雑 |
| **当面ローカル継続** | しばらく `localStorage`/ローカル DB のみ | すぐ進める | 共有・AI サーバー実行ができない＝柱が立たない |

**論点**：
- **オフライン対応**はどこまで必須か？（Q-ARCH-3）
- 立ち上げ速度を取るなら BaaS、長期の自由度を取るなら自前、UX 最重視ならローカルファースト。
- AI プロキシ（Q-AI-3）の置き場所はこの決定に従属する。

> Web サービス展開時の指針（将来）：立ち上げ速度なら BaaS、長期の自由度なら自前、UX 最重視ならローカルファースト。
> AI プロキシ（Q-AI-3）の置き場所もこの段階で確定する。**現フェーズでは決めない。**

## 4. フロントエンドの内部構成

現状は素の React Context + バニラ CSS。スケール時の方針（🟡 提案・Q-ARCH-4）：

- **状態管理**：機能増で Context が重くなれば軽量ライブラリ（Zustand / Jotai 等）へ。サーバーデータは
  データ取得層（TanStack Query 等）で分離。
- **スタイル**：DESIGN.md のトークン（CSS 変数）を維持。必要に応じ CSS Modules 等で分割。
  デザインシステムの一貫性が最優先。
- **ルーティング**：ビュー増に応じて導入を検討。
- これらは**段階導入**。プロトタイプの構成を一気に置き換えない。

## 5. モノレポ構成（提案）

pnpm workspaces を用いた将来像（🟡 提案・Q-ARCH-5）：

```
tascal/
├── packages/
│   ├── core/        # 共有ドメイン・型・状態・APIクライアント（プラットフォーム非依存）
│   ├── ui/          # 共有UIコンポーネント & デザインシステム
│   ├── web/         # Vite Web アプリ
│   ├── desktop/     # Tauri シェル
│   ├── mobile/      # 💤 将来
│   └── server/      # バックエンド（API / AIプロキシ / ジョブ）
├── docs/
└── pnpm-workspace.yaml
```

- 現在の `src/` は移行時に `packages/web`（+ 共有分を `core`/`ui`）へ整理する。
- いきなり分割せず、**バックエンド or デスクトップを足すタイミングで workspaces 化**する。

## 6. ビルド / 配布 / CI

- Web：静的ホスティング（現状の `vite build` 成果物）。
- Desktop：Tauri の各 OS ビルド（mac/win/linux）。署名・自動更新は要検討（💤 / Q-ARCH-6）。
- CI：現状の GitHub Actions（`pnpm install --frozen-lockfile` → build）を拡張し、
  テスト・各プラットフォームビルドを段階的に追加。

---

## 7. テスト戦略 🟡 提案

- ユニット：**Vitest**（`core` のセレクタ・日付・リスク算出など純粋ロジック中心）。
- コンポーネント / E2E：**Playwright**（主要フロー）。
- 方針：純粋関数（selectors/lib）を厚くテスト、UI は重要フローに絞る。

---

## 8. セキュリティ / コンプライアンス

- **AI/外部 API キーはサーバー側のみ**。クライアント・リポジトリに置かない。
- 個人情報（氏名・メール・電話）をログに出さない（組織ポリシー準拠、`CLAUDE.md`）。
- 認証情報のハードコード禁止。本番操作は確認フローを経る。
