# ADR-0001: コミットメントを第一級エンティティとして表現する

- **状態**: 承認
- **日付**: 2026-06-19
- **関連**: Q-PROD-2（open-questions.md）。Q-PROD-3 / Q-AI-1 と連動。

## 背景 / 課題
Tascal の核（柱③）は、タスクを「やること」でなく「誰が・何を・いつまでに引き受けたか＝約束（コミットメント）」として扱うこと。
現状の `Task`（`done:boolean`＋`title`＋`due`）では「これは顧客への約束」「1 つの約束が複数の作業に枝分かれする」を表現できない。
M4（コミットメント可視化）はこのスキーマの上に建つため、表現方法を先に確定する必要がある（未確定のまま実装するとデータ移行コストが発生）。

論点（Q-PROD-2）：コミットメントを (a) Task の属性拡張で表すか、(b) 別エンティティにするか。`softDue` / `stakeholder` を持つか。

**前提となるコンセプト**：Tascal は「一人経営・マルチタスク」を**前提**に置く。これは「**一人ではやり切れない規模**」を相手にする状況を意味する。
その規模をあえて前面に可視化し、AI でマルチタスクを可能にして「コミットメント最大化」の思考へユーザーを導く——
というプロダクト思想（2026-06-19 のビジョン更新「AI 格差をなくし、AI をより身近にする」）に立つ。

## 検討した選択肢
- **案A：Task 属性拡張**（当初の暫定方針）。Task に `status`/`owner`/`stakeholder`/`softDue` を足し、Task そのもの＝約束とみなす。
  - 長所：実装最小、既存 `src/`・`localStorage` を延伸、移行が軽い。
  - 短所：「1 約束＝複数作業」を表現できない。**現状の一人運営の行動（1 タスク＝1 約束が支配的）に最適化**するため、
    プロダクトが超えようとする規模を自己否定しかねない。
- **案B：別エンティティ（Commitment が複数 Task を束ねる）**。約束（Commitment）と作業（Task）を分離する。
  - 長所：「1 約束＝複数作業／複数文脈」を第一級で表現できる。AI が「どの約束を、どこまで運んだか」を語れる。
    可視化の単位が「約束」になる。マルチユーザー・AI 社員にも素直に拡張できる。
  - 短所：実装・移行コストが大きい。手入力前提だと設定量が増え柱①（設定最小）と緊張する。
- **案C：ハイブリッド**（実装は属性拡張、将来 B へ切り出す逃げ道）。中間案。

## 決定
**案B を採用**：コミットメントを**第一級エンティティ**として表現し、1 つの Commitment が複数の Task（作業／文脈）を束ねられる構造にする。
これは「**一人ではやり切れない規模 ＝ 1 約束が複数作業に枝分かれ**」というコンセプトの核を直接体現する。
案A は現状行動への最適化であり、プロダクトが拡張しようとする世界を自己否定するため不採用。

**両立条件（柱①「設定最小」との緊張の解消）= 段階開示・原則任意**：
- リッチな項目（`owner` / `stakeholder` / `softDue` 等）は**スキーマには持つ**が、UI は**段階開示**し、原則**任意・既定値**で運用する。
  単独ユーザーは**今と同じ軽さ**で使える。構造の妥当性検証は**データモデルとダッシュボード**で行い、入力を強制しない。
- `done:boolean` → `status:'todo'|'doing'|'done'|'blocked'` へ移行（互換変換、`tascal.v1`→`v2`）。
- 遅延（late）は `status` に入れず、`due` 超過かつ未完を**派生算出**（保存しない。Q-PROD-3 の方向）。
- `owner` / `stakeholder` / `softDue` / `ownerType` は任意。構造化された `stakeholder`・共有は M2（マルチユーザー）、
  `ownerType:'ai'` は AI 着手フェーズで後方互換に追加する。

**シーケンス（重要）**：
- **コミット可視化（M4）と AI 最小形（M3 / D0）は分離を維持する**。**AI を実装する前に、人手（段階開示）でこの構造の妥当性を検証する**（de-risk）。
- **最終形（落としどころ・記録）**：リッチな約束モデル ＋ **AI による構造の充填** ＋ 段階開示。
  AI が owner／相手／分解／リスクを下書きし、人は承認するだけ——という形を目標とする。
  今回は意図的に「**構造検証 → AI 充填**」の順に分け、構造を確かめてから AI を乗せる。

## 影響
- **反映先**：`vision.md`（ミッション・柱③）、`product-spec.md` §2、`data-model.md`（Commitment エンティティ追加・段階開示）、
  `roadmap.md`（M4 を「構造＋手動検証・AI 非依存」に再定義、AI 警告／ブリーフィングは M3 側へ）、
  `open-questions.md`（Q-PROD-2 を ✅・決定ログ）、提案 `docs/proposals/2026-06-19-feature-brushup-proposal.md`（§4.1 を本 ADR で更新）。
- **新たな作業**：Commitment ↔ Task の関連、`status` マイグレーション（v1→v2）、段階開示 UI、ダッシュボードの「約束」単位集約。
- **リスク**：別エンティティ化の実装・移行コスト。AI 不在の M4 期間は構造が人手依存になるため、**段階開示・原則任意**で柱①の負担を抑える前提。
- **覆す場合のコスト**：データ移行（Commitment 廃止 → Task へ統合）と UI 再設計。覆す場合は新 ADR で supersede する。
